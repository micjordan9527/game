# 业务专题内容规范

适用于新增或完整重写的业务专题；本轮先落实会员账号和代理系统。此文件仅供编写与验收，不展示到网站。

## 元数据

- `src/data/articles.ts` 与 Markdown frontmatter 的 title、description、category、tags、audience、difficulty、date、updatedAt 必须一致。
- 日期使用 `YYYY-MM-DD`。改版保留最初发布日期，更新 updatedAt；不以发布日期冒充案例发生日期。
- 使用已有栏目与难度枚举。slug、已有文章 URL 与课程模块 ID 保持稳定，避免破坏收藏、搜索和学习记录。
- 正文不再写一级标题；页面 ArticleHero 已提供唯一的 h1。

## 正文顺序

1. 一句话解释：说明解决什么问题。
2. 适合谁看：明确读者及实际任务。
3. 学习路径：已有入门资料 → 本文 → 示例或原型 → 可复用模板。
4. 概念与边界：区分相似概念，说明业务角色、数据口径与假设。
5. 状态与处理：逐项列出状态、进入条件、用户反馈、后台动作、恢复条件与记录。
6. 流程图：至少一张可实际渲染的 Mermaid 图，包含异常或复核路径。
7. 虚构示例：编号、时间、金额或状态明确标为教学示例，计算前后一致。
8. 异常场景：列明触发、核实依据、处理动作、负责人或权限边界、关闭证据。
9. 评审检查清单：可以逐项验收，并链接到可复制、导出的模板。
10. 相关资料：使用有明确关系的术语、文章、模板、原型或案例；不强行凑齐类型。
11. 风险与注意事项：说明示例适用范围、隐私、权限、审计与外部契约边界。

## 示例与事实

- 教学方案使用“本例约定”，不能写成所有平台的通用规则；明确状态、时区、统计周期、生效时间、精度和版本。
- 案例材料只描述已有证据能证明的页面或改动。没有测量数据，不声称收益、转化率或效率提升。
- 存在外部技术事实时核对实际使用的服务官方文档，并标明来源和适用版本；本轮两篇采用业务教学模型，不套用特定厂商契约。
- 账号状态不等于身份验证状态；会员归属不等于代理层级；佣金计算、审核、入账、外部付款分别记录。
- 公开内容不包含内部规划、维护话术、真实身份资料、凭据或具体风控识别阈值。

## 关联与验收

- 新专题应出现在文章库、全站搜索和产品栏目；相关模板能够返回专题。
- 新增术语必须有明确解释和实际用途，避免把泛词匹配成错误释义。
- 类型检查、内容检查、专题结构检查通过后才发布。专题结构检查从本轮两篇开始，不一次性强制重写旧文。
- 浏览器验证：唯一 h1、目录跳转、Mermaid 渲染、所有正文站内链接及锚点、模板复制与下载、搜索、390/1440 宽度无整页横向溢出。
- 重试、重复操作或权限示例说明的是教学约束，不据此声称真实系统已经实现。
- 推送后核对 Netlify 部署提交和线上内容，再更新执行清单为已上线。

## 案例分析

- 先核对本地原型或图片，分别写材料观察、对照位置、判断依据、建议验收；没有实测结果时不写收益或效率提升。
- 说明原型、静态截图、生成式视觉提案的边界。无法访问的旧版保留未验证项，不替代为臆测。
- 案例包含问题背景、原有结构与角色任务、方案依据、材料入口和可复制下载的评审清单。
- 案例与文章、模板、工作流使用明确的双向关联，学习状态保留原 slug。
- 内容检查验证来源文件存在、四段分析字段齐全及关联目标有效；浏览器验证原型、大图、清单操作与手机显示。
