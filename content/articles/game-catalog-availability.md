## 一句话解释

游戏出现在目录里，只表示它对当前页面可能可见，不保证当前账号、区域、币种和厂商服务都允许进入。登录失败也不等于游戏已经下架。

## 适合谁看

维护游戏目录的运营、设计状态与错误反馈的产品、对接厂商的开发，以及定位“看得到但进不去”问题的客服和测试人员。

## 把可见和可玩拆开

| 判断层 | 需要确认 | 示例状态 |
|---|---|---|
| 目录配置 | 游戏是否上架到目标站点和栏目 | 前台可见、隐藏、待发布 |
| 厂商服务 | 游戏或厂商入口是否维护 | 可用、维护中、状态未知 |
| 账号条件 | 登录、验证、风控和权限是否满足 | 允许、账号受限、需验证 |
| 区域与币种 | 当前区域、币种、钱包模式是否支持 | 支持、不支持、需转换 |
| 登录请求 | token、回调、时间和签名是否有效 | 成功、失败、结果未知 |

赛事暂停、盘口关闭或注单停止受理属于体育内容与交易状态，不能直接映射成游戏目录下架。游戏目录、游戏登录和具体玩法状态应使用各自的标识与原因码。

## 正常检查路径

取得稳定的游戏 ID 和厂商 ID → 查询目标站点的目录配置 → 查询厂商可用状态 → 校验账号、区域、币种与钱包条件 → 发起一次带业务请求号的登录 → 保存厂商响应、原因码和时间。

显示名称和图片可以修改，排查与日志应保留稳定 ID。前端根据原因码给出可理解提示，但不能把所有失败都显示为“游戏已下架”。

## 虚构示例：目录可见但无法进入

演示游戏 `GAME-DEMO-21` 在站点 A 目录中可见，厂商状态为维护，登录接口返回原因码 `PROVIDER_MAINTENANCE`。前台显示“维护中，可稍后重试”，客服按游戏 ID 和请求号查询同一结果。

另一个账号访问相同游戏时返回 `ACCOUNT_RESTRICTED`，只说明该账号条件不同，不能据此把游戏对所有用户下架。示例原因码用于说明结构，不代表任何现有厂商的真实协议。

## 异常处理

- 厂商查询超时：状态显示未知，先查询原请求或厂商状态，不直接改成维护或下架。
- 目录缓存未更新：对照配置版本与前台实际版本，避免用旧缓存判断。
- 币种不支持：明确币种条件和可用替代入口，不自动转换或改变钱包余额。
- 登录 token 过期：重新取得合法会话，但不要重复创建资金转账或注单动作。
- 多个名称指向同一游戏：以稳定 ID 关联状态、日志和处理记录。

## 风险与注意事项

实际截图可以证明某时刻的显示状态，不能证明全部账号或全部地区都可用。GPT 示意图只用于解释状态关系。真实可用性还需要接口响应、厂商状态、账号条件和端到端登录证据共同判断。
