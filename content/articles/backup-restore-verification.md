## 一句话解释

备份是保存可恢复的数据和依赖，恢复验证是实际证明这些材料能在指定环境重建一致的业务。备份任务成功，不等于恢复已经通过。

## 适合谁看

制定备份与容灾方案的运维、负责数据库和任务的开发，以及需要判断恢复范围与验收依据的项目负责人。

## 先列出恢复所需材料

| 材料 | 需要核对 | 常见遗漏 |
|---|---|---|
| 数据库 | 全量、增量或日志链、恢复点、引擎版本 | 有增量但缺少对应全量 |
| 对象与附件 | 对象清单、版本、权限和校验值 | 数据库引用的附件已缺失 |
| 程序与配置 | 代码版本、表结构、配置版本 | 恢复后程序无法读取旧结构 |
| 密钥依赖 | 密钥标识、权限与可用性 | 有加密备份却无法解密 |
| 外部业务 | 通道、厂商、消息、异步任务的截止状态 | 数据恢复后重复执行旧任务 |

密钥材料需要独立保护和受控使用，不能把明文密钥与备份一起放在普通下载目录。备份策略还应包含保存期、访问范围、异地或独立故障域以及删除验证。

## RPO 和 RTO 要区分目标与实测

RPO 描述可接受的数据丢失时间范围；RTO 描述恢复到约定服务状态所需时间目标。实际演练记录需要定义故障时刻、最后一致恢复点、恢复起点与验收完成时刻。

虚构演算：故障发生于 10:00，最后可确认的一致恢复点为 09:55，时间差为 5 分钟。10:00 开始恢复，10:40 通过定义的验收，耗时 40 分钟。这只说明该假设场景，不代表本站或任何生产系统达到这些指标；外部订单仍需逐条核对。

## 在隔离环境中实际恢复

选择备份集与恢复点 → 校验文件和日志链 → 在隔离环境恢复数据库与附件 → 加载匹配的程序和配置 → 禁止对外付款、回调和批任务自动执行 → 核对结构、数量与业务约束 → 记录耗时与失败 → 形成可重复的恢复证据。

隔离环境使用受限账号和网络规则，避免恢复出来的定时任务向真实第三方再次发起资金动作。恢复完成后再按需要放行受控查询。

## 不能只核对数据库能否启动

| 检查 | 例子 |
|---|---|
| 结构与版本 | 表、索引、约束、迁移版本是否匹配 |
| 文件完整性 | 备份校验值、附件是否可读取 |
| 关系完整性 | 钱包流水可关联订单，审批可关联动作 |
| 业务一致性 | 余额与流水按既定账务模型核对，不存在无主资金记录 |
| 状态边界 | 恢复点前后处理中、未知和已完成订单是否可定位 |
| 重放安全 | 消息、回调和任务恢复后沿用原业务键 |

## 恢复点后的第三方结果怎么处理

数据库回到 09:55，第三方可能已经处理 09:55 至 10:00 的请求。不能把本地不存在的记录全部当作未执行再发一遍。需要通过原业务号、第三方查询与对账材料确认，补齐缺失证据，并在授权流程下修复差异。

切回正式服务前，记录恢复点、差异范围、验证人、剩余问题与观察窗口。若存在未解决资金差异，应明确对应业务动作的限制，不让“服务已恢复”掩盖数据问题。

## 风险与注意事项

演练使用脱敏或受控数据，记录访问与销毁。恢复能力需要定期实测，备份介质、密钥和版本改变后重新验证。本文是方法说明，本站不连接生产数据库，也没有真实恢复测量结果。
