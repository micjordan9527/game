## 一句话解释

幂等让同一业务重试得到同一处理结果；乱序控制避免旧事件覆盖新状态；补偿是在证据确认后，用关联记录修复已经发生的不一致。三者不能靠一个“重试”按钮解决。

## 适合谁看

处理支付、钱包、注单和第三方回调的开发、测试，以及需要定义未知状态和人工处理边界的产品。

## 业务键和请求号分开

| 标识 | 稳定范围 | 示例 |
|---|---|---|
| 请求号 | 一次技术请求 | 每次重试可有不同 request_id |
| 业务动作号 | 同一资金或状态动作 | 同笔扣款重试使用原 transaction_id |
| 对象号 | 被操作的订单或注单 | 一个订单可能有扣款、退款等多个动作 |
| 事件版本 | 同一对象的状态顺序 | 结算 v2 更正 v1，不能按接收顺序判断 |

唯一键通常包含租户、第三方命名空间和业务动作号，必要时包含动作类型。同一个局号不一定只产生一笔扣款，不能将它误作所有事件的唯一键。相同键的金额、币种或对象不一致属于冲突，需要拒绝并复核。

## 幂等需要原子边界

验签并校验范围 → 以唯一约束争抢业务键 → 检查对象状态与版本 → 在事务内保存业务结果、账务流水及事件待发记录 → 提交 → 返回持久化结果。若由异步消费者继续处理，要保证事件可恢复投递，消费者也要去重。

“先查没有，再插入”在并发下可能被两个请求同时通过。数据库唯一约束、事务或具备同等保证的机制才能决定唯一执行者；缓存锁失效也不应产生第二笔资金动作。完成后的重试返回原结果；仍处理中时返回可查询的原动作号。

## 虚构示例：超时之后不是再扣一次

演示扣款 `TX-DEMO-001` 金额 100，币种为同一演示币种。平台已记账，响应在网络中丢失。厂商重试原业务号时，读取原扣款结果，余额不能再减 100。若同号变成金额 120，报冲突，不能以“已处理”返回一个与请求不符的成功。

如果查询也超时，状态保持“结果未知”。恢复后核对原业务号、唯一键记录和账务流水。只有确定未执行且规则允许，才重新驱动原动作；确定已执行则恢复原结果。

## 乱序事件怎样处理

| 场景 | 控制方式 | 证据不足时 |
|---|---|---|
| 旧结算晚到 | 验证版本，保留原始事件但不覆盖新状态 | 查询厂商当前结果 |
| 退款先于扣款 | 验证原事务依赖，进入待关联队列 | 不凭空生成原扣款 |
| 回调和拉单重叠 | 同一业务键与版本合并 | 冲突进入差异核对 |
| 两个消费者并发 | 唯一约束与状态条件更新 | 一方读取已持久化结果 |

没有版本号时，需要契约约定的状态转换条件、原事务关系或权威查询。发生时间和接收时间都应保存，但单靠本地接收时间不能证明业务先后。

## 补偿和重试的区别

重试仍是原动作；补偿是纠正已确认结果的新关联动作。例如重复入账已发生，不能删掉一笔历史流水假装没有发生。应核对原始证据，按审批规则创建冲正或差额调整，并关联原流水、差异单和处理原因。

补偿金额不得超过经确认允许纠正的范围。补偿本身也要幂等，未知结果需查询；审批通过不代表执行完成。余额不足或关账后调整，需要进入明确的异常流程。

## 风险与注意事项

去重记录保留时长应覆盖第三方最大重放窗口和对账需要，不能任意清空。日志不保存密钥。失败后核对真实结果，不能只凭 HTTP 状态确认资金是否变化。涉及账务的演算还需要数据库与故障注入验证，本站说明图不代替实现证明。
